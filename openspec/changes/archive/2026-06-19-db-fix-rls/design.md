## Context

The Supabase setup contains a `public.spatial_ref_sys` table automatically generated by PostGIS. PostgREST exposes all tables in the `public` schema. The `spatial_ref_sys` table does not have Row Level Security (RLS) enabled, triggering a security vulnerability alert because unauthenticated or authenticated users could potentially mutate this reference data if no RLS is enforced.

## Goals / Non-Goals

**Goals:**
- Fix the security vulnerability by enabling RLS on the `public.spatial_ref_sys` table.
- Define an RLS policy that allows read access (SELECT) for everyone (or authenticated/anon users) since spatial reference systems data is public reference information.
- Prevent any user (other than postgres/superuser) from mutating (INSERT, UPDATE, DELETE) the table via the API.

**Non-Goals:**
- Modify the structure of `public.spatial_ref_sys`.
- Change any PostGIS functionality.

## Decisions

- **Enable RLS**: We will run `ALTER TABLE public.spatial_ref_sys ENABLE ROW LEVEL SECURITY;`.
- **Read Policy**: Create a policy `spatial_ref_sys_select_policy` allowing `SELECT` for all users (`USING (true)`).
- **Write Policy**: No write policy will be created for the web roles, effectively denying INSERT/UPDATE/DELETE.

## Risks / Trade-offs

- **Risk**: PostGIS upgrades or migrations might assume superuser access and bypass RLS, which is standard. If the application explicitly needs to insert into `spatial_ref_sys` via PostgREST (highly unlikely), it would fail.
- Mitigation: Reference data is normally populated by the `postgis` extension creation and updates. Standard application roles don't need write access.
